## ۱) تصمیم معماری اصلی

**قالب بلوکی (Block Theme / Full Site Editing) با هدف حداقلی‌سازی override قالب‌های ووکامرس و تمرکز منطق در `theme.json` + فیلترهای رسمی وردپرس/ووکامرس.**

### چرا قالب بلوکی؟ (شواهد ۲۰۲۶-۱۰-۱۲)

1. **ووکامرس مدرن بلوکی است.** مستندات رسمی ووکامرس مسیر «Block Theme Development» را با فهرست قالب‌های بلوکی (`archive-product.html`، `single-product.html`، `page-cart.html`، `page-checkout.html`، `order-confirmation.html` و …) منتشر می‌کند و صراحتاً می‌گوید قالب‌های پیش‌فرض وو «با هر قالب بلوکی کار می‌کنند» و **لازم نیست** قالب آن‌ها را override کند (منبع: `developer.woocommerce.com/docs/theming/block-theme-development/…` و بحث رسمی تیم وو: «themes won't *need* to»).
2. **کاهش ریسک نگهداری.** قاعدهٔ رسمی ووکامرس: هر override فایل PHP باید با هر نسخهٔ ووکامرس هم‌گام شود (`@version`) و در System Status هشدار می‌دهد. قالب بلوکی این بار را حذف/کم می‌کند.
3. **استاندارد جاری وردپرس.** `theme.json` نسخهٔ ۳ در WP 7.1.3 (تأییدشده در سورس هسته: `WP_Theme_JSON::LATEST_SCHEMA = 3`) و قالب‌های بلوکی مسیر رسمی توسعه هستند.
4. **RTL و طراحی سیستم‌محور.** توکن‌های رنگ/فاصله/تایپ در `theme.json` + CSS با ویژگی‌های منطقی، کم‌ترین کد و بیشترین سازگاری RTL را می‌دهد.
5. **قاعدهٔ «قالب ≠ افزونه».** قالب بلوکی بدون PHP نمایشی، مرز قالب/افزونه را تمیز نگه می‌دارد (بدون CPT/بلوک سفارشی/فرم).

### چرا نه قالب کلاسیک خالص؟

- ووکامرس برای صفحه‌های سبد/تسویه از **بلوک‌های Cart/Checkout** استفاده می‌کند که در قالب کلاسیک نیازمند قالب‌های PHP و override های نسخه‌محور است.
- سبک‌های ووکامرس در قالب بلوکی از `theme.json` (`styles.blocks["woocommerce/*"]`) قابل هدف‌گیری‌اند؛ در کلاسیک باید با سلکتورهای کلاس‌محور نوشته شوند که مستندات وو در سپتامبر ۲۰۲۶ صراحتاً از آن‌ها **منع** می‌کند («HTML internals are private»).

### چه چیزی از مزیت کلاسیک استفاده می‌شود؟

- PHP فقط برای «چسبِ کارکرد»: `after_setup_theme`، enqueue، فیلترها، صفحهٔ تنظیمات، helperهای نمایشی فارسی. **بدون** CPT، بدون بلوک سفارشی، بدون شورت‌کد، بدون فرم.

## ۲) مرز قالب و افزونه (سیاست سخت)

| قابلیت | جای درست | در این قالب؟ |
|---|---|---|
| چیدمان، رنگ، تایپوگرافی، فاصله‌ها | قالب (`theme.json` + CSS) | ✅ |
| الگوهای بخش (hero، دسته‌بندی‌ها، اعتماد) | قالب (`patterns/*.php`) | ✅ |
| قالب‌های بلوکی محصول/سبد/تسویه | قالب (override حداقلی، فقط اگر ضروری) | ✅ (کمینه) |
| استایل بلوک‌های ووکامرس | قالب (`theme.json`) | ✅ |
| نمایش فارسی اعداد/تاریخ (فقط لایهٔ نمایش) | قالب (`inc/persian.php`) | ✅ |
| صفحهٔ تنظیمات قالب (نمایشی) | قالب (Settings API) | ✅ |
| نوع‌محتوای سفارشی، تاکسونومی | **افزونه** | ❌ |
| فرم تماس/خبرنامه/عضوگیری | **افزونه** | ❌ |
| ویش‌لیست، مقایسه، اطلاع‌ازموجودی | **افزونه** | ❌ |
| درگاه پرداخت، ارسال، مالیات، فاکتور | **افزونه** | ❌ |
| سئوی متا (title/description/canonical/OG) | **افزونه** (یا ووکامرس) | ❌ |
| فیلتر چندوجهی محصول | **افزونه/بلوک‌های وو** | ❌ |
| تحلیل‌گر، پیکسل، پشتیبانی زنده | **افزونه (با ملاحظهٔ حریم خصوصی)** | ❌ |

**دلیل سخت‌گیری:** قاعدهٔ اعلامی مخزن قالب‌های وردپرس: «Themes are not allowed to include plugins and non-design related functionalities such as forms… Shortcodes, custom post types, and custom blocks are not allowed in themes» (منبع: `developer.wordpress.org/themes/releasing-your-theme/`، آخرین بازبینی ۲۰۲۶-۰۵-۱۹). حتی اگر قالب برای انتشار در مخزن وردپرس ارائه نشود، این قاعده تضمین‌کنندهٔ **قابل حمل بودن داده** است: با تغییر قالب، محصولات/سفارش‌ها/تنظیمات وو و دادهٔ افزونه‌ای سر جای خود می‌مانند.

## ۴) جریان داده و نقاط اتصال (Hooks/APIs)

```text
درخواست → هستهٔ وردپرس → حل قالب (WP Template Hierarchy)
        → templates/*.html (قالب بلوکی)
        → بلوک‌ها (هسته + ووکامرس در صورت فعال بودن)
        → فیلترهای قالب (inc/): render_block, woocommerce_*, wp_get_attachment_image_attributes
        → style.css/theme.json (global styles) → HTML نهایی راست‌چین
```

| هدف | API / محل پیاده‌سازی | یادداشت |
|---|---|---|
| سیستم طراحی | `theme.json` v3 | تنها مرجع رنگ/تایپ/فاصله؛ متغیرهای CSS تولیدشدهٔ هسته (`--wp--preset--*`) استفاده می‌شوند |
| بارگذاری استایل/فونت | `wp_enqueue_style` + `wp_style_add_data('path')` + `wp_enqueue_block_style` | الگوی رسمی قالب‌های بلوکی هسته (بررسی‌شده در `twentytwentyfive/functions.php` و `wp-includes/script-loader.php`) |
| اعلام پشتیبانی وو | `add_theme_support('woocommerce')` + قالب‌های بلوکی وو | بدون ویرایش افزونه |
| بهبود نمایش وو | `woocommerce_*` hooks و `render_block` | مثلاً `woocommerce_sale_flash`, `formatted_woocommerce_price`, `woocommerce_cart_item_*` |
| نمایش اعداد فارسی | فیلترهای خروجی قیمت (`raw_woocommerce_price`?, `formatted_woocommerce_price`, `wc_price`) و فیلترهای متن | فقط نمایش؛ `datetime`/JSON-LD دست نمی‌خورد |
| صفحهٔ تنظیمات | Settings API: `register_setting`, `add_settings_section`, `add_settings_field`, `settings_fields` | capability: `manage_options` (یا `edit_theme_options`)، sanitize اجباری |
| حالت بدون ووکامرس | بررسی `class_exists('WooCommerce')` + نگهبان‌ها | بلوک‌های وو در نبود افزونه چیزی رندر نمی‌کنند؛ الگوها نباید شکسته شوند |
| اجرای lint/آزمون | ابزارهای `tools/` + Playground + GitHub Actions | جزئیات در `MR369L/docs/TEST_AND_QUALITY_FA.md` |

## ۵) سیستم طراحی (خلاصهٔ پیش‌نویس)

- **تایپوگرافی:** Vazirmatn (OFL-1.1، محلی، `font-display: swap`) + استک جانشین فارسی `"Vazirmatn", "IRANSans", Tahoma, system-ui, sans-serif`؛ ارتفاع خط بدنه ≥ ۱٫۸ (فارسی)، سرتیتر ۱٫۲۵–۱٫۳؛ `letter-spacing: 0`؛ مقیاس تایپ فلوئید با `clamp()` در `theme.json`.
- **رنگ:** پالت حداقلی شامل `base`/`contrast`/`accent`/`muted`/`surface`/`success`/`warning`/`error` با تضمین کنتراست AA (۴٫۵:۱ متن، ۳:۱ عناصر تعاملی/متن بدون زیرخط)؛ همه در `theme.json` تا در ویرایشگر هم قابل استفاده باشند.
- **فاصله:** مقیاس ۴/۸/۱۲/۱۶/۲۴/۳۲/۴۸/۶۴ به‌صورت preset؛ بدون magic number پراکنده در CSS.
- **شکل و لبه:** `border-radius` حداقلی (سبک مینیمال) با توکن؛ `box-shadow` بسیار محدود؛ تفکیک با فاصله و خط، نه سایه‌های سنگین.
- **چیدمان:** `contentSize` ≈ ۷۲۰px، `wideSize` ≈ ۱۱۴۰px، `rootPaddingAwareAlignments` فعال؛ شبکهٔ محصول ۲ ستونی موبایل → ۳/۴ ستونی دسکتاپ با فاصلهٔ منظم.
- **جهت:** همه‌چیز با ویژگی‌های منطقی؛ `rtl-fixes.css` فقط برای موارد استثنایی (آیکون‌های جهت‌دار، اسکرول‌بار افقی، اعداد درون متن LTR).
- **حرکت:** انیمیشن حداقلی؛ احترام به `prefers-reduced-motion: reduce` (خاموش‌سازی انتقال‌ها).

## ۶) سیاست اختیاری‌بودن (Owner-controlled)

- هر قابلیت اختیاری = یک گزینه در صفحهٔ تنظیمات با پیش‌فرض **خاموش یا محافظه‌کارانه**.
- گروه‌بندی صفحات: «نمایش فروشگاه» / «فارسی و راست‌چین» / «کارایی» / «دسترس‌پذیری و پیشرفته».
- هر گزینه در `docs/FEATURE_CATALOG_FA.md` شناسه دارد: `planned` / `implemented-disabled` / `enabled` / `deferred` / `not applicable`.
- **ممنوعیت صریح:** هیچ گزینه‌ای برای قابلیتِ پیاده‌نشده یا آزمون‌نشده در رابط نمایش داده نمی‌شود.

## ۷) امنیت در سطح معماری

- هیچ درخواست بیرونی، هیچ telemetry، هیچ اسکریپت رهگیری.
- نوشتن‌ها: فقط از طریق Settings API (nonce داخلی `settings_fields` + capability + sanitize).
- خروجی‌ها: escape بر اساس بافت (`esc_html`, `esc_attr`, `esc_url`)؛ در قالب‌های بلوکی، خروجی بلوک‌ها توسط هسته escape می‌شود و ما فقط CSS/توکن ارائه می‌کنیم.
- بدون `eval`, بدون `unserialize`, بدون درج کد از ورودی؛ فایل‌های قالب PHP نبودنشان (HTML) سطح حمله را کم می‌کند.
- بررسی‌های خودکار ایستا در CI برای الگوهای پرخطر (نبود nonce در نوشتن، نبود escape در echo).

## ۸) گزینه‌های بررسی‌شده و رد‌شده (Alternatives)

| گزینه | چرا رد شد |
|---|---|
| قالب کلاسیک PHP خالص + override های وو | بار نگهداری override ها با هر نسخهٔ وو؛ خلاف توصیهٔ رسمی وو؛ سلکتور‌های کلاس‌محور |
| قالب فرزند بر پایهٔ قالب موجود | قالب والد مسئول نگهداری نیست و بخشی از تصمیم پروژه است (هویت مستقل لازم است) |
| قالب با بلوک‌های سفارشی اختصاصی (محصول، اسلایدر) | خلاف قاعدهٔ «بلوک سفارشی در قالب»؛ قفل‌شدگی محتوا به قالب |
| افزودن CPT `product` اختصاصی | فاجعهٔ داده‌ای؛ ووکامرس مرجع محصول است |
| صفحه‌ساز (Elementor) | وابستگی سنگین، کارایی، خروج از دامنه |
| کتابخانهٔ JS برای اسلایدر/منو | بلوک‌های هسته کافی‌اند؛ جاوااسکریپت کم = INP بهتر |
| CDN برای فونت | نبود دسترسی در ایران، حریم خصوصی، وابستگی بیرونی |

## ۹) حالت‌های خطا و رفتار «بدون ووکامرس»

1. اگر ووکامرس غیرفعال نباشد: قالب مثل یک قالب وبلاگ/سایت شرکتی کار می‌کند؛ قالب‌های `*-product*` هرگز استفاده نمی‌شوند و «فروشگاه» در منو نمایش داده نمی‌شود (الگوی منو دستی است).
2. بلوک‌های وو در بخش‌ها (مثلاً سبد کوچک در هدر) در نبود افزونه چیزی رندر نمی‌کنند؛ بنابراین **هدر پیش‌فرض بدون سبد کوچک** طراحی می‌شود و افزودن آن یک **الگوی اختیاری** است.
3. هیچ `function_exists`/`class_exists` ای که فقط برای «سکوت خطا» باشد اضافه نمی‌شود؛ هر نگهبان باید دلیلی مستند داشته باشد.
4. پیام‌های راهنما برای مالک (مثلاً «برای نمایش فروشگاه، ووکامرس را نصب کنید») فقط در پیشخوان، و با capability مناسب.

## ۱۰) پیامدهای معماری (Trade-offs)

| پیامد مثبت | هزینه/ریسک |
|---|---|
| نگهداری کم، سازگاری بالا با نسخه‌های آیندهٔ وو | کنترل جزئی طراحی وو از طریق override کم است → با `theme.json` و الگوها جبران می‌شود |
| امنیت بالاتر (نبود PHP نمایشی) | برخی رفتارهای پویا فقط با فیلتر PHP ممکن است |
| RTL/Style Variation با یک فایل | تغییرات ظاهری نیازمند درک `theme.json` است |
| صفر جاوااسکریپت اختصاصی | بعضی تعامل‌ها (مثلاً استیکی هدر) یا با CSS حل می‌شوند یا حذف می‌شوند |
| بستهٔ سبک | کاربران عادت‌کرده به صفحه‌ساز ممکن است انعطاف کم‌تری ببینند |
