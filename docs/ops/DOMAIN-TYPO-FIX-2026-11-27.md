# ریشهٔ قطعیِ سایت پیدا شد: تایپوی دامنه در پایگاه‌داده
### ۶ آذر ۱۴۰۵ — گزارش تشخیص و بستهٔ اصلاح

> **تصحیح مهم:** فرض قبلی که «یک دامنهٔ جدید به‌عنوان addon domain اضافه شده» **غلط بود**. مالک تأیید کرد فقط یک دامنه وجود دارد: `sarzaminaryan.ir`. آن دامنهٔ دیگر، **تایپو** است.

---

## ۱. ماجرا در یک خط

در جدول `wp_options`، مقدار `home` و `siteurl` به‌جای `sarzami**n**aryan.ir` نوشته شده `sarzami**ny**aran.ir` — یک **y** اضافه. آن رشته یک دامنهٔ واقعی نیست، پس وردپرس هر بازدید را به آدرسی می‌فرستاد که در DNS وجود ندارد.

```
آنچه باید باشد:   https://s a r z a m i n a r y a n .ir
آنچه نوشته شده:   https://s a r z a m i n y a r a n .ir     ← y اضافه
```

## ۲. چرا سایت حتی با دامنهٔ درستِ خودش هم باز نمی‌شود

وردپرس در هر درخواست، آدرس کانونیک را از `siteurl`/`home` می‌سازد. اگر این مقدار به دامنهٔ دیگری اشاره کند، دو اتفاق بد می‌افتد:

1. مرورگر کاربر را به آن دامنه **ریدایرکت** می‌کند.
2. کوکی‌های ورود و بخش زیادی از لینک‌های داخلی به همان دامنهٔ مرده می‌چسبند.

و چون `sarzaminyaran.ir` هیچ رکورد DNS ندارد (`NXDOMAIN`)، نتیجه «سایت باز نمی‌شود» است — دقیقاً همان چیزی که دیده شد.

> این توضیح، کامل‌تر از توضیح قبلی است: پیش‌تر «دامنه به vhost وصل نیست» گفته شده بود. سنجش امروز: پورت ۸۰ و ۴۴۳ هر دو بازند و سرور پاسخ می‌دهد؛ ولی صفحهٔ پیش‌فرض cPanel و سپس بسته‌شدن TLS دیده می‌شود. **محرک اصلی همان ریدایرکت وردپرس است.**

## ۳. دامنهٔ تایپی کجای پایگاه‌داده نشسته (شمارش دقیق از خروجی ۲۵ نوامبر)

| جدول | ردیف | چه چیزی |
|---|---:|---|
| `wp_options` | **۲** | `siteurl` و `home` ← **همین دو تا سایت را می‌خوابانند** |
| `wp_options` | ۱ | `litespeed.conf.crawler-sitemap` |
| `wp_options` | ۱ | `googlesitekit_search-console_settings` (سریالایز) |
| `wp_options` | ۳ | گزارش/پشتیبان افزونهٔ `sa-editorial-fix` (سریالایز، تاریخی) |
| `wp_posts` | ۲۰۱ | آدرس **تصویرها** در متن: جاذبه ۳۱، راهنما ۶۷، صفحه ۵، ناوبری ۱، پیوست ۳، بازبینی ۹۴ |
| `wp_postmeta` | ۱۰۵ | `_menu_item_url` ۱، `sa_schema_contained_in` ۱۰، `_sa_backup_json` ۹۴ |
| `wp_users` | ۱ | `user_url` کاربر مدیر |
| `wp_iaa_reports` | ۱۰۷ | `post_url` گزارش‌های ممیزی اکتبر (تاریخی) |
| `wp_clarity_collect_events` | ۴۶٬۷۵۴ | payload خام آنالیتیکس (بی‌اثر روی نمایش) |

**نکتهٔ حیاتی:** `guid` نوشته‌ها **پاک است** (۰ مورد). یعنی هیچ لینک دائمی خراب نشده و مهاجرت لازم نیست — فقط مقدار تنطیمات و چند آدرس تصویر.

## ۴. راه‌حل — فقط دو مقدار، در phpMyAdmin

**اگر فقط همین دو خط را اجرا کنید، سایت برمی‌گردد:**

```sql
UPDATE IR_options
   SET option_value = REPLACE(option_value, 'sarzaminyaran', 'sarzaminaryan')
 WHERE option_name IN ('siteurl', 'home');
```

بعد از آن: **تنظیمات ← پیوندهای یکتا ← ذخیره** (بدون تغییر چیزی، فقط برای بازسازی قواعد`.htaccess`).
و اگر از صفحهٔ مدیریت در دسترس نیست، `wp_options` را همان بالا نگه دارید و صفحهٔ اصلی را در پنجرهٔ ناشناس باز کنید.

## ۵. بستهٔ کامل (بازبینی‌شده) برای اصلاح بقیه

فایل آماده: **`docs/ops/sql/domain-typo-fix.sql`**

ساخت دوباره:
```bash
python3 tools/ops/domain_typo_fix.py --out docs/ops/sql/domain-typo-fix.sql
```

این فایل ۴ گام دارد:

| گام | چه می‌کند |
|---|---|
| ۰ | **پشتیبان** می‌گیرد (`CREATE TABLE … AS SELECT` برای هر جدول متأثر) |
| ۱ | **پیش‌شمارش**: قبل از هر تغییری می‌گویید چند ردیف قرار است عوض شود |
| ۲ | **اصلاح** با `REPLACE()`، محدود به شرط مشخص (فقط ردیف‌های مربوط) |
| ۳–۴ | **راستی‌آزمایی**: شمارنده‌ها باید صفر شوند و `siteurl`/`home` درست شوند |

دستور بازگردانی هم در انتهای فایل به‌صورت کامنت آمده است.

### چرا ایمن است

- جایگزینی **هم‌طول** است: `sarzaminyaran` → `sarzaminaryan`، هر دو **۱۳ نویسه**. پس مقدارهای سریالایز (`a:2:{…}` با `s:25:"…"`) نمی‌شکنند، چون طول رشته‌ی داخلشان عوض نمی‌شود.
- هر `UPDATE` با `WHERE` محدود شده؛ هیچ ردیفی خارج از فهرست بالا لمس نمی‌شود.
- قبل از `UPDATE`، پشتیبان ساخته می‌شود.

### آنچه آزمایش شد

بسته روی یک **کپی واقعی از دادهٔ سایت** (خروجی ۲۵ نوامبر) اجرا و بررسی شد:

| بررسی | نتیجه |
|---|---|
| هر ۵ شمارندهٔ باقی‌مانده | **۰** |
| `siteurl` / `home` پس از اجرا | `https://sarzaminaryan.ir` ✅ |
| مقدار سریالایز Site Kit | ساختار سالم، `s:25` هنوز ۲۵ نویسه ✅ |
| `guid` نوشته‌ها | دست‌نخورده (۰ تغییر) ✅ |
| لینک تصویر نمونه | `…/sarzaminaryan.ir/wp-content/uploads/…` ✅ |

> توجه: مقادیر `payload` در Clarity و `_sa_backup_json` هم عوض می‌شوند ولی فقط داخل **متن** هستند؛ هیچ کلید یا شناسهٔ دیتابیس تغییر نمی‌کند.

## ۶. بعد از اجرا — ترتیب بازرسی

```bash
python3 tools/ops/site_health.py
```
انتظار: `ok` یا حداقل `http 200` روی `https://sarzaminaryan.ir`.

سپس در پیشخوان:
1. **تنظیمات ← عمومی**: بررسی کنید «آدرس وردپرس» و «آدرس سایت» هر دو `https://sarzaminaryan.ir` باشند.
2. **تنظیمات ← پیوندهای یکتا**: ذخیره (بازسازی `.htaccess`).
3. **LiteSpeed Cache ← Purge All**.
4. اگر صفحهٔ اصلی باز شد ولی تصویرها نه: یک‌بار «ابزارها ← سلامت سایت» و سپس پاک‌سازی کش مرورگر/افزونهٔ کش.

## ۷. اگر سایت برنگشت — سه فرض بعدی

1. **`home`/`siteurl` در جدول دیگری هم هست؟** بعضی نصب‌ها `wp_options` را با پیشوند دیگری دارند. با `SELECT * FROM information_schema.tables WHERE table_name LIKE '%options'` پیشوند را تأیید کنید.
2. **`.htaccess` خراب شده:** فایل را به `.htaccess.bak` تغییر نام دهید و از **تنظیمات ← پیوندهای یکتا** دوباره ذخیره کنید.
3. **SSL:** اگر مرورگر خطای گواهی داد، AutoSSL را برای `sarzaminaryan.ir` اجرا کنید. آخرین گواهی معتبر: ۷ اکتبر ۲۰۲۶.

## ۸. درس ثبت‌شده برای پروژه

**پیش از هر تشخیص زیرساختی، مقدار `home`/`siteurl` را از پایگاه‌داده بخوانید.** یک تایپوی ۱۳ نویسه‌ای، دو روز عیب‌یابی DNS، SSL و cPanel را به خودش مشغول کرد.

*هیچ نوشتن زنده‌ای انجام نشده است. این سند و اسکریپت فقط پیشنهاد و بازبینی‌اند؛ اجرا در phpMyAdmin با تصمیم مالک است.*
