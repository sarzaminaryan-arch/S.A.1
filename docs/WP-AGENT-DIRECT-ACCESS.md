# دسترسی مستقیم ایجنت به وردپرس (پل ایجنت)

> **سند مرجع.** هر نشست تازه پیش از هر کاری روی سایت زنده این فایل را بخواند.
> وضعیت: **فعال و آزموده** از ۱۵ نوامبر ۲۰۲۶ (۲۴ آبان ۱۴۰۵). قالب زنده: 2.22.78. ایجنت از 2.22.76 به‌روزرسانی قالب را خودش با روال امن (بخش ۴-ب) انجام می‌دهد.
> راهنمای فنی دستورها: `tools/wp-agent/README.md`.

## ۱. خلاصه در سه خط

- ایجنت سایت **sarzaminaryan.ir** را مستقیم می‌خواند: همهٔ نوع‌ها، همهٔ وضعیت‌ها، متا و برچسب‌ها.
- ایجنت مقاله را مستقیم در وردپرس می‌گذارد، اما **فقط به‌صورت پیش‌نویس**. انتشار فقط کار مالک است.
- پیش از هر تغییر در ظاهر، ساختار یا محتوای موجود، **اول پشتیبان** گرفته می‌شود و بعد تغییر انجام می‌شود. بازگشت با یک فرمان ممکن است.

## ۲. قواعد مالک (دستور ۱۴ نوامبر ۲۰۲۶؛ نقض نکن)

| موضوع | قاعده |
|---|---|
| خواندن | آزاد است. |
| مقالهٔ تازه | فقط `draft`. هیچ فرمان انتشار یا حذفی وجود ندارد. |
| زباله‌دان (از قالب ۲.۲۲.۷۴، دستور مالک ۱۵ نوامبر) | فقط `trash` برای نسخهٔ تکراری‌ای که نشانی‌اش از قبل مبدأ یک ۳۰۱ با مقصد منتشرشده است. پرچم `owner_approved_trash` و پشتیبان لازم است. حذف همیشگی وجود ندارد. |
| LiteSpeed (از قالب ۲.۲۲.۷۴) | فقط خواندن تنظیمات کش. تنها کلیدهای خزنده (`crawler`، `crawler-sitemap`، `crawler-crawl_interval`، `crawler-load_limit`) با پشتیبان نوشتنی‌اند. |
| تغییر ظاهر یا ساختار | اول پشتیبان از وضع قبلی، بعد تغییر. پیش از هر تغییر ظاهری به مالک بگو چه چیزی از چه مقداری به چه مقداری می‌رود. |
| متن مقالهٔ منتشرشده | مستقیم عوض نمی‌شود. `draft-copy` (پیش‌نویس بازنویسی کنار اصل) بساز. `owner_approved_live_edit` فقط با دستور صریح و مکتوب مالک در همان نشست. |
| کد قالب | فقط از راه نسخهٔ تازه و Release. نسخهٔ قبلی روی GitHub پشتیبان است. |
| نصب قالب (دستور مالک ۱۵ نوامبر: «خودت کامل انجام بده… قبل از هر به‌روزرسانی با UpdraftPlus پشتیبان بگیر») | فقط با روال امن بخش ۴-ب: پشتیبان کامل UpdraftPlus (پایگاه‌داده و فایل‌ها) ← نصب Release تأییدشده ← پاک‌کردن کش ← probe بی‌کش ← بازگشت به نسخهٔ قبلی در صورت خرابی. پل بدون پشتیبان موفق پایگاه‌داده در ۶ ساعت گذشته نصب نمی‌کند. |
| متن صفحهٔ زنده (دستور مالک ۱۵ نوامبر) | فقط پس از راستی‌آزمایی، با `owner_approved_live_edit` و پشتیبان. هر تغییر یک سطر در `docs/live-site/CHANGELOG.md`. |
| دورهٔ Core Update (تا حدود ۴ آذر ۱۴۰۵) | تغییر ظاهری، تغییر نشانی و حذف انبوه ممنوع است. |
| رمزها | فقط در GitHub Secrets. هرگز در چت نخواه و هرگز در مخزن ننویس. |
| متن | قواعد `AGENTS.md` (بندهای ۸ تا ۱۲) برقرار است. پل خودش واژه‌های ممنوع را رد می‌کند. |

## ۳. چطور کار می‌کند

```
نشست Arena (sandbox بدون دسترسی شبکه به سایت)
  │  ۱) فایل کار: tools/wp-agent/jobs/<YYYYMMDD-NN-نام>.json  (+ متن در tools/wp-agent/outbox/)
  │  ۲) git push روی شاخهٔ نشست
  ▼
GitHub Actions — workflow «WP agent» (.github/workflows/wp-agent.yml)
  │  رمزها از Secrets: SA_SITE_URL, SA_USER, SA_APP_PASSWORD
  │  اجرا: python3 tools/wp-agent/wp_agent.py run-job <job>
  ▼
sarzaminaryan.ir/wp-json/sa-agent/v1   (inc/agent-bridge.php در قالب فرزند)
  │  احراز هویت: Application Password کاربر sa-agent (مدیر کل)
  │  پشتیبان سمت سایت: ابزارها ← «پشتیبان‌های ایجنت» (نوع خصوصی sa_agent_backup)
  ▼
نتیجه: tools/wp-agent/results/<همان نام>.json  (workflow روی همان شاخه commit می‌کند)
پشتیبان سمت runner: artifact خصوصی wp-agent-backups-<run> (۹۰ روز)
```

## ۴. دستور کار ایجنت (گام‌به‌گام)

1. اگر متن لازم است: `tools/wp-agent/outbox/<slug>.html` (و متا در `<slug>.meta.json`).
2. فایل کار با **نام یکتا** بساز. هر فایل فقط یک بار اجرا می‌شود.

   ```json
   {"note": "پیش‌نویس بجنورد", "steps": [
     {"cmd": "ping"},
     {"cmd": "draft", "type": "post", "title": "…", "content_file": "tools/wp-agent/outbox/bojnord.html"}
   ]}
   ```

3. `git add` و `commit` کن، بعد `git push origin <شاخهٔ نشست>`.
4. اجرا را دنبال کن و نتیجه را بخوان:

   ```bash
   gh run list --workflow wp-agent.yml --limit 3
   gh run watch <id> --exit-status
   git pull --ff-only origin <شاخه>
   cat tools/wp-agent/results/<نام>.json
   ```

5. هر نوشتن را در `docs/live-site/CHANGELOG.md` یک سطر ثبت کن.

**فرمان‌ها:**

| فرمان | کار |
|---|---|
| `ping` | آزمون اتصال |
| `list` | فهرست با فیلتر `type` / `status` / `search` / `slug` / `modified_after` |
| `inventory` | همهٔ محتوا، همهٔ وضعیت‌ها |
| `get` | یک نوشته کامل، همراه متا |
| `draft` | ساخت پیش‌نویس تازه |
| `draft-copy` | پیش‌نویس بازنویسی کنار یک نوشتهٔ منتشرشده |
| `update` | متا یا برچسب، و متنِ پیش‌نویس‌ها؛ با پشتیبان |
| `backups` | فهرست پشتیبان‌ها |
| `restore` | بازگشت از پشتیبان |
| `theme-mods` | خواندن یا تغییر تنظیمات ظاهر؛ با پشتیبان |
| `trash` | فقط نسخهٔ تکراریِ پشت ۳۰۱ → زباله‌دان؛ `--owner-approved-trash`؛ با پشتیبان (۲.۲۲.۷۴) |
| `litespeed` | خواندن تنظیمات LiteSpeed؛ `--set` فقط کلیدهای خزنده؛ با پشتیبان (۲.۲۲.۷۴) |
| `probe` | خواندن عمومی یک یا چند نشانی: وضعیت، robots، canonical، توضیح، شمار H1، کش |
| `seo-scan` | اسکن همهٔ نشانی‌های نقشهٔ سایت: عنوان، توضیح، H1، alt (خالی و ناموجود جدا)، اسکیما، زمان |
| `index-gate` | خواندن تصمیم قاعدهٔ index/noindex هر صفحهٔ شهرستان و دلیلش (`manual` > `thin_text` > `no_places`) (۲.۲۲.۷۵) |
| `updraft` | وضعیت آخرین پشتیبان UpdraftPlus؛ `--backup` پشتیبان کامل تازه (۲.۲۲.۷۵) |
| `theme-update` | روال امن نصب نسخهٔ تازهٔ قالب (بخش ۴-ب) (۲.۲۲.۷۵) |
| `relations-audit` | پیوند شهرستان یا دیدنی به والدِ منتشرنشده یا ناموجود (`sa_city_id`، `sa_province_id`) (۲.۲۲.۷۶) |
| `cache-purge` | پاک‌کردن کش LiteSpeed: `--all` یا `--id N` (۲.۲۲.۷۷) |
| `content-audit` | فقط خواندنی: جملهٔ تکراری، سهم جملهٔ قالبی، تناقض اقلیم و عدد ناممکن در صفحه‌های شهرستان؛ خروجی صف اصلاح است (منطق در `tools/wp-agent/content_audit.py`) |
| `run-job` | اجرای یک فایل کار |

### ۴-ب. روال امن به‌روزرسانی قالب

یک گام در فایل کار:

```json
{"cmd": "theme-update", "expected_version": "2.22.78", "owner_approved_theme_update": true,
 "backup_first": true, "backup_wait": 1500,
 "probe": ["/", "/blog/", "/city/isfahan-city/"], "rollback_to": "2.22.77"}
```

1. **پیش از نصب:**
   - Release `sarzaminaryan-child-v<نسخه>` باید در GitHub ساخته شده باشد (CI موفق).
   - صفحه‌های probe پیش از نصب خوانده می‌شوند.
2. **پشتیبان:**
   - پشتیبان کامل UpdraftPlus (پایگاه‌داده، افزونه‌ها، قالب‌ها، بارگذاری‌ها) گرفته می‌شود و تا `backup_wait` ثانیه منتظر پایانش می‌ماند.
   - بدون WP-Cron هم کار می‌کند: پاسخ HTTP اول بسته می‌شود و پشتیبان در همان درخواست ادامه می‌یابد.
3. **نصب:**
   - `Theme_Upgrader` هستهٔ وردپرس بستهٔ Release را نصب می‌کند.
   - اگر نصب نیمه‌کاره بماند، وردپرس خودش نسخهٔ قبلی را برمی‌گرداند (`temp_backup`).
4. **کش:** پس از نصب، کش LiteSpeed پاک می‌شود. قالب از ۲.۲۲.۷۷ این کار را با تغییر نسخه خودش هم انجام می‌دهد.
5. **probe سلامت:**
   - با پارامتر `?sa_probe=<زمان>` از کش رد می‌شود، پس صفحه با کد تازه ساخته و سنجیده می‌شود.
   - همه باید ۲۰۰ و بی‌خطای PHP باشند.
6. **بازگشت در صورت خرابی:**
   - `rollback_to` نسخهٔ قبلی را از Release خودش نصب می‌کند.
   - اگر آن هم نشد، بازگشت کامل از پشتیبان UpdraftPlus در پیشخوان انجام می‌شود (تنظیمات ← پشتیبان‌گیری UpdraftPlus ← بازگردانی).

**استقرار بدون پشتیبان تازه (از ۲.۲۲.۱۱۶):** دستور مالک (۲۸ آبان ۱۴۰۵) این بود که برای
به‌روزرسانی قالب پشتیبان کامل تازه گرفته نشود. گام کار همان می‌ماند با یک کلید اضافه:

```json
{"cmd": "theme-update", "expected_version": "2.22.117", "owner_approved_theme_update": true,
 "allow_without_backup": true, "probe": ["/", "/city/kazerun/"], "rollback_to": "2.22.115"}
```

`allow_without_backup: true` فقط شرط «پشتیبان کمتر از ۶ ساعت» را رد می‌کند؛ نصب هنوز
از همان `Theme_Upgrader` هسته می‌گذرد و اگر probe ناسالم باشد، `rollback_to` از همان
مسیر نصب می‌شود. برای بازگشت، همان کلید خودکار روشن است (بازگشت هرگز به پشتیبان
گره نمی‌خورد).

**سابقه:**
- کار ۱۲: ۲.۲۲.۷۵ ← ۲.۲۲.۷۶؛
- کار ۱۳: ← ۲.۲۲.۷۷؛
- کار ۱۴: ← ۲.۲۲.۷۸؛
- کار ۱۲۷: ← ۲.۲۲.۱۱۶ (نخستین تلاش؛ ۴۰۹ «نسخه منتشر نشده» چون پیش از انتشار ریلیز دوید). نتیجه در `results/` می‌ماند؛ کارِ یک‌بارمصرف است و دوباره اجرا نمی‌شود.
- کار ۱۲۸: ← ۲.۲۲.۱۱۷ (همان بسته + رفع تست تصاویر؛ بدون پشتیبان تازه، بازگشت به ۲.۲۲.۱۱۵ مسلح).

هر سه سالم و هر کدام حدود ۴ تا ۷ دقیقه.

**خواندن عمومی سریع، بدون این مراحل:** `fetch_page` روی صفحه‌ها یا `/wp-json/wp/v2/...`.

### ۴-ت. تصاویر شهرستان (WebP ۴:۳ زیر ۱۰۰ کیلوبایت)

```json
{"cmd": "photos", "city_id": 325}
{"cmd": "photos-optimize", "owner_approved": true, "limit": 30}
{"cmd": "photos-optimize", "owner_approved": true, "photo_id": [4800, 4828]}
{"cmd": "photos-manage", "owner_approved": true, "photo_id": 4800, "action": "hide"}
```

- `photos` فقط می‌خواند: `bytes`، `mime`، `width`/`height`، `lead`، `hidden`، `order`،
  `visible`، `url`، و شمارنده‌های `over_100kb`/`non_webp` تا بدانیم چه چیزی جا مانده.
- `photos-optimize` هر عکس را با GD به WebP ۴:۳ (۸۰۰×۶۰۰) و ≤ ۹۹٬۰۰۰ بایت تبدیل می‌کند؛
  `limit` سقف هر کار است (پس یک کار سه-چهار گامی همهٔ کتابخانه را می‌پوشاند) و `force`
  تبدیل دوباره را اجباری می‌کند. فایل خام قبلی فقط وقتی پاک می‌شود که در `post_content`
  شهرستان ارجاع مستقیم نداشته باشد.
- `photos-manage` یک عکس را مدیریت می‌کند: `hide`/`unhide`/`lead`/`detach`/`trash`
  (زباله‌دان برگشت‌پذیر، هرگز حذف دائمی) یا `update` با `place`/`highlight`/`tag`/`order`.
- هر دو مسیر روی سایت `owner_approved: true` می‌خواهند و به همان دسترسی‌های ویرایش
  نوشته و آپلود فایل بسته‌اند.

### ۴-پ. ویرایش زندهٔ دسته‌ای (حذف تکرار و یادداشت تولید)

1. خواندن: یک کار `get` برای حداکثر ۱۰ شناسه (فقط خواندنی).
2. ساخت پیش‌نمایش: `python3 tools/wp-agent/build_fix_batch.py results/<read>.json outbox/<batch> [rewrites.json]`
   - خروجی هر صفحه: HTML تمیزشده و `changes.txt`.
   - `summary.json` شمار واژه، جملهٔ تکراری و یادداشت را پیش و پس از اصلاح نشان می‌دهد، به‌همراه این کنترل‌ها: تعادل برچسب‌ها، جفت توضیح‌های گوتنبرگ و idempotent بودن.
3. کار نوشتن: برای هر صفحه یک `update` با `expected_modified_gmt` (از همان خواندن) و `owner_approved_live_edit`؛ سپس `cache-purge` و `probe` (با `?sa_probe=N`) و در آخر `content-audit`.
4. کلیدهای ایمنی در خود فایل کار:
   - `"not_before": "YYYY-MM-DDTHH:MM:SSZ"`: کار تا آن زمان اجرا نمی‌شود و نتیجه‌ای هم ثبت نمی‌کند. اجرای روزانهٔ ۰۶:۳۰ UTC روی `main` آن را برمی‌دارد. سقف «۱۰ صفحه در روز» با همین کلید رعایت می‌شود.
   - `"rollback_on_fail": true`: اگر گامی رد شود یا `probe` پس از تغییر ناسالم باشد، همهٔ پشتیبان‌های همین کار، از تازه‌ترین، با `/restore` برگردانده می‌شوند و فهرستشان در `rollback` نتیجه ثبت می‌شود. probe ناسالم یعنی هر یک از این‌ها: وضعیت غیر از ۲۰۰، نبودِ title، `noindex` یا تعداد H1 غیر از ۱.
5. صفحه‌ای که یادداشت‌نویسی در کل متنش پخش است (مثل شوش و شوشتر) با حذف درست نمی‌شود. چنین صفحه‌ای به صف بازنویسی ویرایشی می‌رود.

## ۵. اجزا

| جزء | مسیر |
|---|---|
| ماژول سمت سایت | `wp-content/themes/sarzaminaryan-child/inc/agent-bridge.php` (در `functions.php` بعد از `security.php` بارگذاری می‌شود) |
| تست | `wp-content/themes/sarzaminaryan-child/tests/test-agent-bridge.php` (در CI انتشار قالب) |
| Application Password | در `inc/security.php` دیگر خاموش نیست. فقط کاربرانی که `edit_others_posts` دارند (ویرایشگر و مدیر) آن را دارند. سرآیند جایگزین `X-SA-Authorization` هم پذیرفته می‌شود. |
| کلاینت | `tools/wp-agent/wp_agent.py` (فقط کتابخانهٔ استاندارد پایتون؛ رمز را با `***` می‌پوشاند) |
| اجراکننده | `.github/workflows/wp-agent.yml` (روی push در `tools/wp-agent/jobs/**.json`؛ هم‌زمانی سریالی) |
| نتیجه‌ها | `tools/wp-agent/results/` |

**مسیرهای REST** (`/wp-json/sa-agent/v1`):

| مسیر | مجوز |
|---|---|
| `GET ping`، `GET posts`، `GET post/{id}` | `edit_posts` |
| `POST post/{id}`، `POST post/{id}/draft-copy`، `POST post/{id}/trash`، `POST draft`، `GET backups`، `GET backup/{id}`، `POST restore/{id}` | `edit_others_posts` |
| `GET/POST theme-mods` | `edit_theme_options` |
| `GET/POST litespeed` | `manage_options` |
| `GET index-gate`، `GET relations-audit` | `edit_posts` |
| `GET/POST updraft`، `POST cache-purge` | `manage_options` |
| `GET/POST theme-update` | `manage_options` + `update_themes`؛ POST فقط با پشتیبان موفق پایگاه‌داده در ۶ ساعت گذشته |

- هیچ مسیر DELETE وجود ندارد. `post/{id}/trash` فقط نسخهٔ تکراریِ پشت ۳۰۱ را به زباله‌دان می‌برد. بازگردانی از پشتیبان، آن را به‌صورت پیش‌نویس برمی‌گرداند.
- نامک، وضعیت و تاریخ انتشار با پل عوض نمی‌شوند.
- برچسب یا دستهٔ تازه ساخته نمی‌شود.
- متای محافظت‌شده (`_…`، به‌جز `_thumbnail_id`) رد می‌شود.
- هم‌زمانی با `expected_modified_gmt` (پاسخ 409) و `expected_hash` بررسی می‌شود.

## ۷. عیب‌یابی

| نشانه | علت و راه‌حل |
|---|---|
| `Missing repository secrets` در workflow | Secrets ساخته نشده است. مالک: Settings ← Secrets and variables ← Actions. |
| `HTTP 401` | Application Password لغو شده یا نام کاربری اشتباه است. مالک یک رمز تازه می‌سازد و `SA_APP_PASSWORD` را به‌روز می‌کند. |
| `HTTP 404 rest_no_route` | نسخهٔ قالب برای آن فرمان کافی نیست (ستون نسخه در جدول فرمان‌ها را ببین). |
| `HTTP 409 sa_agent_live_content` | تلاش برای تغییر متن زنده. `draft-copy` بساز. |
| `HTTP 409 sa_agent_stale` | نوشته از زمان خواندن عوض شده. دوباره بخوان. |
| فایل کار اجرا نشد | نامش تکراری است و فایل نتیجه دارد. نام تازه بگذار. |
| `theme-update` با `409 sa_agent_need_backup` | پشتیبان موفق UpdraftPlus در ۶ ساعت گذشته نیست. `backup_first: true` بگذار. |
| `updraft --backup` با `409 sa_agent_backup_recent` | پشتیبانی کمتر از دو دقیقه پیش تمام شده. همان کافی است. |
| پس از نصب، صفحه هنوز خروجی قدیمی دارد | کش LiteSpeed است. `cache-purge --all` (یا قالب ≥ ۲.۲۲.۷۷ که خودش پاک می‌کند). |
| `cache-purge` با 409 | افزونهٔ LiteSpeed Cache فعال نیست. |

**قطع دسترسی توسط مالک:** کاربران ← `sa-agent` ← ویرایش ← «رمزهای عبور برنامه» ← «لغو».
