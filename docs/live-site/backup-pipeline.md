# بک‌آپ سبک و پایپ‌لاین انتشار — جایگزین «پشتیبان کامل برای هر تغییر»

**تاریخ ثبت:** ۲۸ آبان ۱۴۰۵ · **نسخهٔ قالب:** 2.22.120 · **وضعیت:** کد نوشته و تست شده؛
نصب زنده و شمارش حجم، پس از تأیید مالک.

## ۱. تصمیم

پیش از این، هر تغییر کوچک دو هزینهٔ حجمی داشت:

| مسیر قدیم | چه چیزی کپی می‌شد | هزینه |
| --- | --- | --- |
| نوشتن روی یک نوشته (`/post/{id}`) | **کل رکورد**: متن کامل (تا ~۱٬۱۰۰ واژه)، عنوان، چکیده و همهٔ متاها در یک رکورد خصوصی `sa_agent_backup` | برای هر صفحهٔ شهرستان یک نسخهٔ کامل، بدون سقف نگه‌داری |
| نصب قالب (`/theme-update`) | **پشتیبان کامل UpdraftPlus**: پایگاه‌داده + کل پوشهٔ `uploads`، و شرط «کمتر از ۶ ساعت» | چند صد مگابایت برای هر ارتقای قالب |
| کار روزانه | هر job، هر نوشتن → یک رکورد پشتیبان تازه | رشد خطی حجم در پایگاه‌داده |

از ۲.۲۲.۱۲۰:

1. **پشتیبان افتراقی** — فقط فیلد/متایی که همان نوشتن واقعاً عوض کرده ذخیره می‌شود.
2. **سیاست نگه‌داری** — ۳ نسخهٔ آخر هر هدف و سقف ۴۰۰ رکورد در کل (فیلترپذیر).
3. **Git جای «بک‌آپ کد»** — قالب و فایل‌های `data/<slug>.json` در گیت‌هاب تگ و تاریخ دارند؛
   بازگشت = نصب همان نسخه از Release (همان `rollback_to` که از قبل بود).
4. **UpdraftPlus فقط زمان‌بندی‌شده** — برای بازگردانی کامل سایت (روزانه/هفتگی)، نه برای هر تغییر.
5. **سنگین‌ها روی رانر** — `build-gates.yml` فیلتر املا، نگهبان قالب، قواعد تصویر و بیلد
   صفحه‌ها را در GitHub Actions اجرا می‌کند؛ سایت فقط هنگام انتشار همان رکوردها درگیر می‌شود.

## ۳. امنیت بازگشت‌پذیری (هیچ‌کدام کم نشد)

| سناریو | مسیر بازگشت |
| --- | --- |
| یک نوشته بد شد | `POST /restore/{backup_id}` روی همان پشتیبان افتراقی — فقط همان فیلد/متا برمی‌گردد |
| چند نوشتهٔ یک job بد شد | `rollback_on_fail` همان job (بدون تغییر) هر پشتیبان آن job را تازه‌ترین‌اول برمی‌گرداند |
| قالب بد نصب شد | `theme-update --version <نسخهٔ قبل>` یا `rollback_to` خودکار وقتی probe ناسالم است |
| کل سایت خراب شد | پشتیبان زمان‌بندی‌شدهٔ UpdraftPlus (دست‌نخورده) |
| متن/دادهٔ گم‌شده در گیت | `git revert <commit>` و انتشار دوبارهٔ همان نسخه |

## ۴. عددهای واقعی (سنجیده‌شده روی هاست، ۲۸ آبان ۱۴۰۵)

منبع: `GET /storage` با قالب ۲.۲۲.۱۲۵ (کارهای ۱۳۹ تا ۱۴۵). هیچ عددی تخمین نیست.

| بخش | حجم واقعی | توضیح |
| --- | --- | --- |
| پشتیبان‌های ایجنت (پایگاه‌داده) | **۶۶۱ رکورد، ۱۵٫۳۴ مگابایت** | میانگین ۲۴ کیلوبایت برای هر رکورد کامل؛ از ۱۵ آبان تا امروز |
| نسخه‌های UpdraftPlus روی دیسک | **۵۱۴ مگابایت** | `wp-content/updraft`: ۴۹۰٫۵ مگابایت فایل نسخه‌ها + ۲۳٫۶ مگابایت خود افزونه |
| رسانه‌ها (`uploads`) | **۲۴۷٫۷ مگابایت، ۸٬۳۵۴ فایل** | ۱۶۵ تصویر بالای ۲۰۰ کیلوبایت |
| پوشهٔ افزونهٔ UpdraftPlus | ۲۳٫۶ مگابایت | فایل‌های زبان (es_CR، bg_BG، …) — هرگز پاک نشود |
| artifactهای رانر (گیت‌هاب) | ۴۸ عدد، ۰٫۴۶ مگابایت | روی هاست نیست؛ نگه‌داری ۹۰ → ۱۴ روز |

**هزینهٔ هر نوشتن پیش از این تغییر** (سنجیده روی ۴۶ صفحهٔ واقعی `outbox`):

| نوع پشتیبان | حجم |
| --- | --- |
| رکورد کامل قدیمی (متن + همهٔ متاها) | میانگین **۱۶٫۵ کیلوبایت** (بیشینه ۳۴٫۶ کیلوبایت) |
| پشتیبان افتراقی تازه (فقط متای تغییریافته) | میانگین **۱۲۷ بایت** |
| نسبت | **۰٫۸٪ حجم قبلی** — یعنی حدود ۱۲۹ برابر کوچک‌تر |

با همین ۶۶۱ رکورد امروز: حجم واقعی ۱۵٫۳۴ مگابایت؛ اگر همان نوشتن‌ها با کد قبلی و
سقف نگه‌داری تازه ثبت می‌شدند، وضع فرقی نمی‌کرد — سود اصلی از این به بعد است:
**توقف رشد** (قبلاً بی‌سقف بود) و هر نوشتن تازه ۱۲۹ برابر سبک‌تر.

**صرفه‌جویی تخمینی در سه ماه آینده** (با آهنگ فعلی: ۱۵۰–۲۰۰ نوشتن در هفته):
پیش از این: ۱۹۰ × ۱۶٫۵ کیلوبایت ≈ ۳٫۱ مگابایت در هفته و **~۴۰ مگابایت در ۱۳ هفته**،
بدون سقف. از این پس: ۱۹۰ × ۱۲۷ بایت ≈ ۲۴ کیلوبایت در هفته و با سقف ۴۰۰ رکورد،
سقف کل **~۵۰ مگابایت** هیچ‌وقت رد نمی‌شود.

**بزرگ‌ترین جای صرفه‌جویی، UpdraftPlus است:** ۴۹۰٫۵ مگابایت برای یک نسخهٔ کامل
(۱۸ آبان) که `uploads` آن تنها ۳۹۸ مگابایت است. با حذف یا انتقال آن (بخش ۶) بیشترین
حجم آزاد می‌شود — و از این پس نصب قالب دیگر نسخهٔ تازه نمی‌سازد.

## ۵. سقف‌ها و تنظیم‌ها

```php
add_filter( 'sa_agent_backup_retention', function ( $limits ) {
    $limits['per_target'] = 3;   // سه نسخهٔ آخر هر نوشته/هدف
    $limits['total']      = 400; // سقف کل رکوردهای پشتیبان
    return $limits;
} );
```

UpdraftPlus: زمان‌بندی پیشنهادی **هفتگی، دیتابیس + فایل‌ها، با نگه‌داری ۲ نسخه**.
این تنظیم در پیشخوان افزونه است (نه در کد قالب) و در گزارش حجم دیده می‌شود.

## ۷. بررسی ابری نسخهٔ ۴۹۰ مگابایتی — نتیجه: روی Drive نیست (۲۷ آبان ۱۴۰۵)

با سه شاهد مستقل بررسی شد (کارهای ۱۵۰–۱۵۳، قالب ۲.۲۲.۱۲۹ تا ۲.۲۲.۱۳۲):

| شاهد | نتیجه |
| --- | --- |
| فهرست فایل‌های Drive برای نسخهٔ `82738db7b8c9` | **۰ فایل** |
| لاگ همان نسخه (`log.82738db7b8c9.txt`) | `Cloud backup selection (1/1): none` و `No remote despatch: user chose no remote backup service` |
| تأیید آپلود در لاگ (`OK: Archive … uploaded to`) | **صفر خط** (به‌جایش `Recording as successfully uploaded` آمده که فقط علامت‌گذاری محلی است) |
| `updraft_last_backup` | `success: true` — گمراه‌کننده: موفقیت محلی، نه ابری |

**حکم:** نسخهٔ کامل ۴۹۰ مگابایتی فقط روی دیسک سرور است و در Google Drive وجود
ندارد. تاریخ آخرین نسخهٔ کاملِ موفق روی Drive: **هیچ نسخه‌ای پیدا نشد** (نه قدیمی،
نه جدید). همچنین کلید `service` در تاریخچهٔ UpdraftPlus این سایت خالی است، در حالی
که تنظیمات `googledrive` را نشان می‌دهد — یعنی آن نسخه با `nocloud` اجرا شده بود.

**تنظیمات واقعی (خوانده‌شده، نه حدس):** `interval=manual`، `interval_database=manual`،
`retain_files=1`، `retain_db=1`، `delete_local=1`، `service=googledrive`.

**ریسکی که در کد افزونه پیدا شد:** `prune_file()` در `backup.php` فایل محلی نسخهٔ
قدیمی را بی‌قید پاک می‌کند و تنها بعد از آن سراغ فضای ابری می‌رود. با
`retain_files=1` یعنی ساختن پشتیبان تازه، آخرین نسخهٔ محلی را از بین می‌برد — و اگر
آپلود ابری (مثل همین مورد) انجام نشود، هیچ نسخه‌ای نمی‌ماند. سد ایمنی در ۲.۲۲.۱۳۲:
`POST /updraft` با `nocloud:true` وقتی خدمت ابری پیکربندی شده باشد ۴۰۹ می‌دهد.

**هیچ فایلی حذف نشد.**

### نکتهٔ ایمنی مهم دربارهٔ ترتیب کارها

تغییر `updraft_interval` از `manual` به `weekly` **قبل** از اصلاح اتصال Drive
خطرناک است: با `retain_files=1` و `delete_local=1`، اولین پشتیبانِ زمان‌بندی‌شده
نسخهٔ محلی تنها را پاک می‌کند و چون آپلود ابری کار نمی‌کند، **هیچ نسخه‌ای نمی‌ماند**.
پس ترتیب درست: اول اتصال Drive → بعد تنظیمات → بعد پشتیبان دستی → بعد تأیید سه‌شاهدی.
تا آن زمان عمداً `interval=manual` مانده است.
