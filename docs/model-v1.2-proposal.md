# پیشنهاد غیرمرجع برای مدل دادهٔ v1.2

**وضعیت:** پیش‌نویس برای بازبینی مالک؛ canonical نیست.
**مرجع جاری تا زمان تأیید:** `data-model/MASTER_DATA_MODEL.md` و `data-model/schema/data-model.yaml` نسخهٔ `1.1`.
**مهم:** این فایل ورودی generator نیست؛ هیچ YAML، JSON، پیکربندی قالب یا دادهٔ سایت را تغییر نمی‌دهد.

## شواهد فنی

- ZIP فرزند نسخهٔ `2.11.44` مقدار `SA_MODEL_VERSION = 1.2` و سرآیند config تولیدی `model v1.2` دارد؛ فایل Master/YAML نسخهٔ `1.2` در مخزن یا ZIP ارائه‌شده موجود نیست.
- config قالب فرزند، هفت فیلد دیدنی را تعریف کرده که در مدل `1.1` نیستند. WXR مورخ `2026-10-08` فقط برای شمارش وجود کلیدهای meta بررسی شد؛ مقدار یا متن مقاله خوانده نشد.
- generator نسخهٔ مرجع `1.1` با config موجود round-trip نمی‌شود. اجرای آن فیلدهای زیر را حذف می‌کرد و حداقل منبع دیدنی را از `0` به `5` برمی‌گرداند؛ فایل پس از آزمون به نسخهٔ قبلی برگردانده شد.
- در WXR، termهای taxonomy و تعداد assignmentها بررسی شد؛ termهای بدون assignment به‌عنوان alias یا مترادف تفسیر نشده‌اند.

## ۱. فیلدهای مشاهده‌شدهٔ دیدنی خارج از مدل 1.1

| فیلد/کلید meta موجود | نوع رابط در config قالب | نوشته‌های دیدنی دارای مقدار از 26 نوشتهٔ منتشر | تصمیم لازم برای مدل |
|---|---|---:|---|
| `english_name` / `sa_english_name` | text | 26 | تعریف نوع، معنا و خروجی schema |
| `attraction_age` / `sa_attraction_age` | text | 26 | حفظ متن‌بودن یا تعریف جداگانهٔ سن/قدمت؛ فعلاً ادغام نشود |
| `attraction_area` / `sa_attraction_area` | text | 26 | تعریف واحد/دامنه و روش اعتبارسنجی؛ عدد فرض نشود |
| `elevation` / `sa_elevation` | number، واحد `m` در config | 13 | تأیید واحد و nullable بودن |
| `access_level` / `sa_access_level` | text | 26 | تعریف مجموعه‌مقادیر یا آزادبودن متن |
| `trail_note` / `sa_trail_note` | text | 26 | تعیین معنای دقیق و طول/اعتبارسنجی |
| `safety_note` / `sa_safety_note` | textarea | 26 | تعیین حدود/نمایش؛ بدون بازبینی محتوای ذخیره‌شده |

**پیشنهاد:** اگر مالک این فیلدها را نگه می‌دارد، آن‌ها را append-only به مدل بعدی اضافه کنیم و type/unit/nullability را صریح بنویسیم. تا آن زمان، نباید generator نسخهٔ 1.1 روی config فعلی اجرا شود.

## ۲. اختلاف termهای taxonomy در WXR

### `attraction_type`

مدل 1.1 دوازده term دارد. WXR نوزده term دارد؛ 12 مورد مدل در WXR هم وجود دارند و هفت مورد زیر اضافه‌اند:

| term افزوده | assignment در WXR | مشاهده |
|---|---:|---|
| `family` | 1 | استفاده شده |
| `recreational` | 1 | استفاده شده |
| `waterfall` | 2 | استفاده شده |
| `bazaar` | 0 | بدون assignment |
| `museum` | 0 | بدون assignment |
| `natural` | 0 | بدون assignment؛ با `nature` یکی فرض نشود |
| `sea` | 0 | بدون assignment |

**پیشنهاد:** سه term دارای assignment فقط به‌صورت تغییر append-only برای تأیید ارائه شوند. چهار term بدون assignment در پایگاه داده دست‌نخورده بمانند تا معنای آن‌ها روشن شود؛ آن‌ها را حذف یا با term دیگری یکی نکنیم.

### `travel_budget` و `travel_duration`

- `travel_budget`: مدل 1.1 سه term دارد؛ WXR دو term اضافهٔ `economy` و `midrange` دارد و هر دو صفر assignment دارند.
- `travel_duration`: مدل 1.1 چهار term دارد؛ WXR چهار term اضافهٔ `one-day`، `three-days`، `two-days` و `weekly` دارد و هر چهار مورد صفر assignment دارند.

**پیشنهاد:** تا وقتی موجودیت/assignment وابسته یا تعریف مالک ارائه نشده، هیچ تبدیل یا ادغام خودکاری انجام نشود. شباهت نام، دلیل کافی برای alias بودن نیست.

## ۳. اختلاف سیاست در Level 7

حداقل‌های مدل 1.1 در برابر config موجود در ZIP فرزند `2.11.44`:

| موجودیت | مدل 1.1: FAQ / منبع / لینک / مختصات | config ZIP: FAQ / منبع / لینک / مختصات |
|---|---|---|
| Province | 10 / 5 / 20 / بله | 3 / 5 / 5 / بله |
| City | 10 / 5 / 10 / بله | 3 / 5 / 5 / بله |
| Attraction | 10 / 5 / 10 / بله | 3 / 0 / 3 / بله |
| TravelRoute | 3 / 2 / 5 / خیر | 3 / 2 / 3 / خیر |
| LocalFood | 3 / 2 / 3 / خیر | 3 / 2 / 2 / خیر |
| Souvenir | 3 / 2 / 3 / خیر | 3 / 2 / 2 / خیر |
| Accommodation | 3 / 2 / 3 / بله | 3 / 2 / 2 / بله |

config فعلی مخزن نیز برای منبعِ Attraction مقدار `0` دارد، در حالی که YAML مرجع `5` دارد. در کد فعلی `sa_gate_split()`، FAQ، مختصات و تعداد لینک داخلی هم advisory می‌شوند؛ بنابراین رفتار اجراشده با فهرست blockerهای مدل `1.1` کاملاً هم‌خوان نیست.

ZIP فرزند `2.11.44` سیاست دیگری را با عنوان مدل `1.2` پیاده می‌کند: FAQ/مختصات/حجم لینک advisory، منابع مشروط به حداقل هر موجودیت، و `missing_content_hygiene` به‌عنوان blocker تازه. این تغییر صرفاً اضافه‌شدن چند فیلد نیست؛ رفتار انتشار را عوض می‌کند.

**تصمیم لازم:** قبل از canonical شدن `1.2`، مالک باید برای حداقل‌های هر موجودیت و blockerهای Level 7 تصمیم روشن بدهد. تا آن زمان، هیچ‌یک از آستانه‌های ZIP به مدل مرجع منتقل نشود.

این تصمیم‌های URL/رابطه‌ای مستقل از مدل داده‌اند و خودبه‌خود بخشی از v1.2 نیستند.

## ۵. موانع ادغام ZIP

- `inc/site-cleanup.php` در ZIP مسیر applyای دارد که می‌تواند صفحهٔ خالی منتشرشده را به زباله ببرد؛ همان فایل مسیر حذف برگشت‌ناپذیر و ویرایش متن ذخیره‌شده هم دارد. تا اصلاح و آزمون مستقل، وارد نسخهٔ قابل‌نصب نشود.
- `inc/content-repair.php` متن نوشته‌های موجود را تغییر می‌دهد و خارج از دامنهٔ فعلی است.
- انتشار خودکار شبکه‌های اجتماعی/ربات تلگرام اثر بیرونی دارد؛ بدون بازبینی جداگانه و تأیید فعال نشود.
- PHP، WP-CLI و staging در دسترس نیستند و runnerهای آزمون ذکرشده در CHANGELOG همراه بسته نیستند؛ ادعاهای زمان اجرا قابل‌بازتولید نیستند.

## گام‌های لازم برای canonical شدن

1. مالک نوع، nullable بودن، واحد، اعتبارسنجی و خروجی schema هفت فیلد را تأیید کند.
2. مالک termهای اضافهٔ `attraction_type` و وضعیت termهای بدون assignment را تعیین کند؛ برای termهای بودجه/مدت نیز alias فرض نشود.
3. سیاست blocker/thresholdهای Level 7 را برای همهٔ موجودیت‌ها تصویب کند.
4. منبع مرجع v1.2 را در `MASTER_DATA_MODEL.md` و YAML ثبت کند؛ سپس JSON و child config را از همان منبع بسازد و آزمون‌های round-trip اضافه کند.
5. آزمون PHP و WordPress را در staging انجام دهد؛ ابزارهای trash، purge، content repair و ارسال بیرونی را تا تأیید جداگانه خارج نگه دارد.
